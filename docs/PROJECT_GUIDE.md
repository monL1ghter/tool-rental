# Как устроен проект Tool Rental

Этот файл объясняет, где что лежит, как работает и в каком порядке проект делался. Его удобно читать перед защитой.

## 1. Что делает приложение

Сервис аренды инструментов. Есть три роли: арендатор (RENTER), арендодатель (LANDLORD) и администратор (ADMIN). Арендодатель выкладывает инструмент, арендатор бронирует его на даты, после возврата участники оставляют друг другу отзывы, у каждого пользователя есть рейтинг. На плохие отзывы можно пожаловаться, администратор их видит.

## 2. Структура папок

```
src/main/java/com/toolrental/
  ToolRentalApplication.java   точка входа (метод main)
  controller/                  принимают HTTP-запросы, вызывают сервисы
  service/                     вся бизнес-логика и проверки
  repository/                  интерфейсы для работы с базой (Spring Data JPA)
  entity/                      классы-таблицы и перечисления (статусы, роли)
  dto/                         формы запросов и ответов (records)
  security/                    JWT и настройка прав доступа
  exception/                   единый формат ошибок
  config/                      тестовые данные и раздача загруженных фото
src/main/resources/
  application.properties            настройки (H2, JWT, загрузка файлов)
  application-postgres.properties   настройки для PostgreSQL
docs/                        презентация и этот файл
.github/workflows/build.yml  автоматическая сборка и проверка API на GitHub
pom.xml                      зависимости и сборка (Maven)
```

## 3. Путь одного запроса

Возьмём `POST /reviews/3/report` (жалоба на отзыв):

1. **Security.** `JwtAuthFilter` читает заголовок `Authorization: Bearer ...`, проверяет подпись токена, достаёт из него id пользователя и роль и кладёт их в контекст безопасности. `SecurityConfig` решает, пускать ли запрос: жалоба требует входа, без токена ответ 401.
2. **Controller.** `ReviewController.report` получает id отзыва из адреса, тело запроса `ReportRequest` и id пользователя из токена. Аннотация `@Valid` проверяет тело: причина обязательна, подробности не длиннее 1000 символов. При ошибке `GlobalExceptionHandler` вернёт 400.
3. **Service.** `ReviewService.report` ищет отзыв (иначе 404), не даёт пожаловаться на свой отзыв (400) и дважды на один и тот же (409), сохраняет жалобу.
4. **Repository.** `ReviewReportRepository` записывает жалобу в таблицу `review_report`. SQL писать не нужно, Spring Data создаёт запросы по названиям методов, например `existsByReviewIdAndReporterId`.
5. **Ответ.** Сервис возвращает `MessageResponse`, контроллер отвечает статусом 201.

Эта схема одинакова для всех эндпоинтов: контроллер только принимает и отдаёт данные, а решения принимает сервис.

## 4. Слои подробно

### entity (таблицы)
| Класс | Таблица | Смысл |
|---|---|---|
| `User` | users | пользователь, email и телефон уникальны, пароль хранится только в виде BCrypt-хеша |
| `Tool` | tool | инструмент: цена за день, залог, цена доставки, рейтинг, число отзывов и аренд |
| `Booking` | booking | бронь: даты, статус, способ получения и оплаты, зафиксированные цены |
| `Review` | review | отзыв по аренде: кто написал, о ком, об инструменте, оценка 1-5, текст |
| `ReviewPhoto` | review_photo | фото к отзыву (имя файла в папке `uploads`) |
| `ReviewReport` | review_report | жалоба на отзыв: причина и подробности |
| `RefreshToken`, `OtpCode`, `PasswordResetToken` | служебные | токены обновления, коды для входа по телефону, токены сброса пароля |

Перечисления: `Role`, `BookingStatus`, `DeliveryType`, `PaymentMethod`, `ToolCondition`, `ReportReason`.

Ограничения на уровне базы: пара (отзыв, автор жалобы) уникальна, пара (аренда, автор отзыва) уникальна. Это защищает от дублей, даже если проверка в коде не сработает.

### dto (формы запросов и ответов)
Наружу сущности не отдаются, только DTO. Они сделаны на `record`, это короткая запись неизменяемого класса, поэтому Lombok не нужен. Правила проверки заданы аннотациями прямо в полях: `@NotBlank`, `@Email`, `@Min(1)`, `@Max(5)`, `@Size`. Внутри каждого DTO-файла лежит группа связанных записей, например `ReviewDto` содержит `CreateReviewRequest`, `ReviewResponse`, `RatingResponse` и другие.

### repository
Интерфейсы без реализации. Примеры:
- `findByTargetIdOrderByCreatedAtDesc` берёт отзывы о пользователе от новых к старым;
- `countOverlapping` (запрос на JPQL) считает, сколько броней пересекается с нужными датами;
- `averageByTarget` считает средний рейтинг пользователя.

В каждом репозитории есть метод `getOrThrow(id)`: ищет запись или сразу бросает 404, чтобы в сервисах не повторять одно и то же.

### service (логика)
- **AuthService**: регистрация, вход по email, телефону или одноразовому коду, обновление и отзыв токенов, восстановление и смена пароля. Вход через соцсети сделан заглушкой, токен соцсети не проверяется.
- **ToolService**: каталог. Фильтры собираются через `Specification`: условие попадает в запрос только для тех параметров, которые переданы. Сортировка: популярные, по цене, новые, по рейтингу. Размер страницы ограничен 50.
- **BookingService**: создание и изменение броней, продление, отмена, подтверждение, выдача и возврат. Подробности в разделе 5.
- **ReviewService**: отзывы, фото, рейтинг, жалобы.
- **UserService**: профиль и переход в арендодатели.
- **FileStorageService**: сохраняет фото в папку `uploads` под случайным именем, принимает только JPEG и PNG.

Все сервисы помечены `@Transactional`: каждая операция выполняется как одна транзакция, при ошибке изменения откатываются.

### security
- `JwtService` создаёт access-токен (30 минут, в нём id и роль) и проверяет его. Refresh-токен живёт 14 дней и хранится в базе, поэтому его можно отозвать при выходе.
- `JwtAuthFilter` читает токен из заголовка запроса. Он нарочно не помечен `@Component`, иначе Spring зарегистрирует его дважды и аутентификация потеряется; фильтр создаётся в `SecurityConfig`.
- `SecurityConfig` задаёт правила: без сессий (stateless), CSRF отключён (токены передаются в заголовке), при отсутствии токена ответ 401. Открыты каталог, чтение отзывов, рейтинг пользователя и /auth/**. Добавлять и менять инструменты могут LANDLORD и ADMIN, раздел /admin/** только ADMIN.
- Роль берётся из токена, поэтому при каждом запросе база для проверки прав не нужна. Проверки вида «это ваш инструмент» делает сам сервис.

### exception
Во всём приложении используется одно исключение `ApiException` (статус и сообщение). `GlobalExceptionHandler` превращает его в JSON вида `{"status": 409, "message": "..."}`. Ошибки проверки полей тоже дают 400 с перечнем полей.

### config
- `DataInitializer` при пустой базе создаёт тестовые данные: администратора, арендодателя, двух арендаторов, инструменты, завершённые аренды и три отзыва. Логины и пароли указаны в README.
- `WebConfig` отдаёт загруженные фото по адресу `/uploads/...`.

## 5. Ключевые правила бронирования

- **Занятость.** Инструмент занят, если на выбранные даты уже есть бронь в статусе PENDING, CONFIRMED или ACTIVE. Тогда ответ 409.
- **Стоимость.** Цена за день × число дней (оба дня считаются) + доставка (если выбрана) + залог. Цены записываются в бронь при создании, поэтому смена тарифа арендодателем уже созданную бронь не меняет.
- **Жизненный цикл.** PENDING → подтверждение арендодателем → CONFIRMED → выдача → ACTIVE → возврат → COMPLETED. Отменить можно в статусах PENDING и CONFIRMED.
- **Возврат денег при отмене.** При оплате при получении возвращать нечего. Если отменил арендодатель или арендатор до даты начала, возвращается вся сумма. Если арендатор отменил в день начала или позже, удерживается половина стоимости аренды.
- **Продление.** Новая дата окончания должна быть позже текущей, а добавленные дни свободны.
- **Кто что может.** Менять и продлевать бронь может только арендатор, подтверждать, выдавать и принимать инструмент только арендодатель, смотреть бронь только участники.

## 6. Три добавленных эндпоинта

| Эндпоинт | Где код | Как работает |
|---|---|---|
| `GET /users/{id}/reviews` | `UserController.getUserReviews` → `ReviewService.getUserReviews` | Проверяет, что пользователь есть (иначе 404), и возвращает отзывы, где он «target», от новых к старым. Открыт без токена. |
| `GET /users/{id}/rating` | `UserController.getUserRating` → `ReviewService.getUserRating` | Считает среднее по оценкам, округляет до одного знака, возвращает также количество отзывов. Если отзывов нет, рейтинг 0.0. |
| `POST /reviews/{id}/report` | `ReviewController.report` → `ReviewService.report` | Нужен вход. Сохраняет жалобу в `review_report`. Ошибки: 400 на свой отзыв, 404 если отзыва нет, 409 при повторной жалобе. Администратор видит жалобы в `GET /admin/reports`. |

**Почему у каждого пользователя есть рейтинг.** Отзывы двусторонние: арендатор оценивает арендодателя и инструмент, арендодатель оценивает арендатора. Поэтому в `Review` есть автор (author), адресат (target) и необязательная ссылка на инструмент (tool). Отзыв арендодателя об арендаторе инструмента не касается, и поле tool у него пустое. Рейтинг инструмента считается по отзывам с tool, рейтинг пользователя по всем отзывам, где он адресат. Рейтинг инструмента хранится прямо в таблице `tool` и пересчитывается при создании, изменении и удалении отзыва, поэтому каталог легко фильтровать и сортировать по рейтингу.

## 7. Как делался проект (по этапам)

1. **Разбор задания.** По ТЗ определены роли, список функций и перечень эндпоинтов.
2. **Проектирование БД.** Выделены сущности и связи, статусы брони, правила для отзывов (по аренде, от обоих участников) и жалоб.
3. **Каркас.** Создан `pom.xml` (Spring Boot, Web, Data JPA, Security, Validation, jjwt, H2, PostgreSQL), настройки `application.properties`, единый формат ошибок.
4. **Безопасность.** Регистрация и вход, JWT, refresh-токены, роли, хеширование паролей BCrypt.
5. **Каталог и бронирование.** Поиск и фильтры, проверка занятости дат, расчёт стоимости, продление и отмена.
6. **Отзывы, рейтинг и жалобы.** Отзывы по завершённым арендам, фото, рейтинг пользователя, жалобы и просмотр их администратором.
7. **Данные, документация, проверка.** Тестовые данные при запуске, README, презентация, автоматическая проверка на GitHub.

## 8. Как проверялась работоспособность

Файл `.github/workflows/build.yml` запускается на GitHub при каждом `push`. Он собирает проект, запускает приложение и делает запросы: каталог, рейтинг пользователя, отзывы, вход, жалоба без токена (401), жалоба с токеном (201), повторная жалоба (409), расчёт стоимости. Результат виден на вкладке **Actions** репозитория. Зелёная галочка значит, что все проверки прошли.

## 9. Возможные вопросы на защите

- **Зачем DTO, если есть сущности?** Чтобы не отдавать наружу лишнее (например, хеш пароля) и чтобы формат API не зависел от структуры таблиц.
- **Почему роль лежит в токене?** Чтобы не обращаться к базе при каждом запросе. Минус: после смены роли нужен новый токен, поэтому `become-landlord` сразу возвращает новую пару токенов.
- **Как защищены пароли?** Хранится только BCrypt-хеш, исходный пароль восстановить нельзя.
- **Что делает `@Transactional`?** Объединяет операции метода в одну транзакцию, при ошибке все изменения отменяются.
- **Почему без Lombok?** Код проще читать и не нужны плагины. Геттеры и сеттеры написаны вручную, DTO сделаны на `record`.
- **Что не реализовано?** Реальная оплата и привязка карт, отправка email и SMS (коды пишутся в лог), чат, споры, верификация документов, программа лояльности.
